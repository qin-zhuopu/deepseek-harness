# Agent Note: the auth gate admits the privileged plane

Status: implemented

English | [中文](2026-09-05-auth-gate-admits-the-privileged-plane.zh.md)

> Scope: the seam between a mounted auth gate and the two loopback-only surfaces that block remote browser configuration — the connection node half's privileged-method pin and the browser settings mirror/scope persistence. Ships with the `dsh-aio` shared-password gate (`DSH_AUTH_SECRET`); the gate plugins themselves are [auth-core](../../../../packages/host/auth-core/README.md), [auth-jwt](../../../../packages/host/auth-jwt/README.md), and [auth-iam](../../../../packages/host/auth-iam/README.md).

## Problem

A dsh web served behind a reverse proxy on a public authority reaches its GUI fine — the `/api` authority fence admits the deployment's declared `trustedHosts` — but the configuration plane stays dark: every `settings.*`/`credentials.*`/`llm.discoverModels` call answers 403 (the privileged-method pin is loopback-only per the [api browser-trust boundary note](2026-07-28-api-browser-trust-boundary.md)), and the browser-side mirror refuses even to try, showing "settings are unavailable in this browser" in the model-provider modal. The [web configuration plane note](2026-07-30-web-config-plane.md) pinned the same rule on both sides. That was correct while no authentication layer existed; once the gate shipped, it became the one thing standing between a signed-in remote operator and the settings page. Two halves had to move together: server admission for the privileged methods, and a client that knows it is admitted (otherwise the browser still refuses to send the calls it is now allowed to make).

## Decision

**Authentication substitutes for loopback at exactly the privileged-method pin.** The connection node half's pin passes the trust fence with an empty trust list; it now additionally admits a request when the optional `authPrincipal` service (provided by `mountAuthSurface` in `dsh-host-auth-core`) reports a presented credential. The `/api` prefix fence and the WebSocket upgrade fences never consult the principal: authentication replaces loopback where loopback was the decision, not the deployment's own `trustedHosts` list. A refused privileged call answers `401 unauthorized` with `WWW-Authenticate: Bearer realm="dsh"` — the sign-in signal — instead of the old 403, and with no gate mounted `authPrincipal` is absent (`readAuthPrincipal` reads it leniently through `ctx.get(name, false)`), so today's loopback-only deployments behave identically apart from the refusal status. `isPrivate` reports a credential PRESENTED, not verified; that is safe precisely because the gate's guard rejects unverified credentials before any route runs, and a lenient read of a credential-less request fails closed at the pin.

**The browser learns its verdict from the gate's own surface.** `mountAuthSurface` registers `GET /auth-state`, reachable only through the guard, answering `{"authenticated":true}`; reaching the handler IS the verdict. The client's connection handle publishes an observable `privatePlane` source: loopback (and non-browser) pages are admitted synchronously; a remote page probes `/auth-state` once on load. The probe verdict — not the HTTP status — is what counts, because an SPA fallback answers HTML `200` for any unclaimed path and the JSON parse refuses it.

**Settings persistence follows the live verdict.** `SettingsDescribeMirror` and `SettingsScopeController` take a `SettingsPersistence` — `'host'`, `'memory'`, or a `PrivatePlaneSource`. The binder passes the connection handle's `privatePlane` for non-loopback pages; every read gate (`load`/`ensure`), write queue (`enqueue`), and derive now consults `persistenceAllows()` per call instead of a constructor-time constant. The plugin subscribes the mirror to the plane source, and `refreshPermission()` flips `unavailable` to `idle` and starts the admission read; the scope re-derives through its existing mirror subscription, so a gate admission mid-session opens every bound row without a reload. The client's probe is one-shot (the page is served to a signed-in browser, so a reload is not expected mid-session), while the mirror/scope machinery deliberately reads the live source, which also admits the fixture transports a plain `'memory'`/`'host'` constant.

**The aio deployment bakes an env-gated HS256 gate.** `dsh-aio` ships `jwt-gate.cordis.patch.yml` (baked by every Dockerfile); the entrypoints append `--patch` only when `DSH_AUTH_SECRET` is set, refusing to start on a secret below the 32-character minimum. The web profile's `package.json` declares `@deepseek-ai/dsh-host-auth-jwt` so the profile-healed resolver finds it. The secret lives in the host's compose environment only; the repo never carries it.

## Alternatives considered

- **Keep the pin loopback-only and admin the config from the host machine.** Rejected: it leaves the deployed product's core loop ("store a key, prompt again") unreachable for exactly the remote deployment the reverse-proxy work was for, and the modal's dead-end copy makes the product look broken rather than locked.
- **Consult `authPrincipal` at the `/api` prefix fence too.** Rejected: the prefix fence answers which authorities the DEPLOYMENT declared; letting any gate presentation bypass `trustedHosts` would silently widen the reachability policy and silently pass Host-forgery probes for the admitted browser. The two policies stay orthogonal, and the tests pin the prefix/upgrade fences to the plain Host/Origin comparison.
- **Treat any HTTP `200` on an admission probe path as admitted.** Rejected: the SPA fallback owns every unmatched path and answers HTML `200` (including for `GET /auth-state` when no gate is mounted), so a status-only probe would open the privileged plane for every anonymous page. The JSON verdict `{authenticated:true}` is only reachable through the guard.
- **Decide persistence once at binder construction.** Rejected: the probe settles after plugin activation, so a constructor-time constant permanently pins a remote page to `memory` even after admission; a live `PrivatePlaneSource` plus `refreshPermission()` opens the plane reactively and keeps the existing mirror-subscription derive path as the only publication site.
- **Deploy the IAM (OIDC) gate on the LAN box.** Rejected for the current deployment: `iam.jereh.cn` is unreachable from 10.1.17.58, and a mounted-but-unreachable gate locks every surface (the guard 401s/redirects everything, including login completion). The HS256 gate has no external dependency; the IAM overlay stays opt-in unchanged.

## Consequences

- A remote signed-in browser gets the full configuration plane (settings, credentials, model discovery, preset authoring, native dialogs) with no reload; an anonymous LAN page still gets 401 + Bearer challenge on the pin and a permanently closed `privatePlane`, so every row stays process-local.
- The refusal status for privileged methods changes 403 → 401. Clients that treated 403 as the refusal answer must read 401 (or the `WWW-Authenticate` header) instead; no in-repo consumer did.
- Two independent policies now guard the configuration plane — reachability (`trustedHosts`) and identity (the gate) — and each remains auditable alone: removing the gate restores the old behavior apart from the status code, and widening `trustedHosts` never opens the pin.
- `dsh-aio` gains a third launch mode (open / IAM / JWT) whose misconfiguration fails at the entrypoint log, and the shared-password gate's security rests entirely on the secret's strength and the proxy's TLS; the HTTPS certificate gap is recorded in the ops journal, not here.
