# Agent Note: Sign dsh in through the Jereh IAM OIDC provider

Status: implemented

English | [中文](2026-09-05-jereh-iam-oidc-integration.zh.md)

## Problem

`dsh-host-auth-jwt` gates the web server with a shared secret: one password for every human and every script. The deployment target is Jereh enterprise SSO — `https://iam.jereh.cn/idp` (test: `iam-test.jereh.cn`) — an OIDC provider whose login starts at `GET /idp/authCenter/authenticate?response_type=token&scope=openid&client_id=EnterpriseDingtalk&redirect_uri=…` and delivers `id_token` (RS256, header `{alg:"RS256",kid:"RS256"}` without `typ`, payload `{sub: employee number, uid, aud, iss, exp, iat, jti, nonce:null}`) in the URL **fragment** of the redirect. Fragment parameters never reach a server, so no server-side redirect handler can read the token. The provider publishes keys at `GET /idp/oidc/getPublicKey` behind `/.well-known/openid-configuration`, returns the literal string `null` for an echoed `state`, and publishes an RSA key with no `alg` member alongside an EC key that carries one. The IAM's own session cookie (`usk`, `Domain=iam.jereh.cn`) is not ours to set or clear. A browser sign-in must verify the token against the provider's published keys and land a session the existing webserver guard seats accept, without replacing the shared-secret gate that scripted clients use.

## Decision

`@deepseek-ai/dsh-host-auth-iam` is a function plugin injecting `webServer` that mounts the same guarded surface as `auth-jwt` through a new shared library package, `@deepseek-ai/dsh-host-auth-core`. `mountAuthSurface()` registers the guard, the upgrade guard, and the logout route as caller-fiber effects from one options object (cookie name, login/logout paths, `secureCookie`, exempt paths, a synchronous `verify`); the two gates differ only in how a token is obtained and verified. Extracting the package required breaking one 66-token jscpd clone: the two logout handlers were identical, so logout moved into `mountAuthSurface`.

The flow is OAuth2 implicit, matching what the IAM speaks. `GET /login` awaits a fresh discovery document (502 page when the provider was never reachable), stores `{state, next}` in an `HttpOnly` `SameSite=Lax` cookie, and redirects to the document's `authorization_endpoint` with `response_type=token&scope=openid&client_id&redirect_uri&state`; `redirect_uri` is rebuilt from the request's leftmost `X-Forwarded-Proto` and `Host`, so a TLS terminator registers the public origin. Because the token arrives in a fragment, `GET /auth/callback` serves a same-origin script page that moves `location.hash` into a `POST` of the same path; the POST handler clears the state cookie, answers provider `error` parameters first (before any fetch), then enforces state **before** token handling — a cross-site form POST cannot carry the `HttpOnly` state, so session fixation refuses with 401 — and only then verifies. The `id_token` itself becomes the session cookie (`dsh_token`, `HttpOnly`, `SameSite=Lax`, `Max-Age=exp−now`); it is also accepted as `Authorization: Bearer`, so the same token satisfies browser and API channels. There is no shared-secret login page in this package: scripted clients keep using `auth-jwt`, and the two gates are alternative deployments, not a combined stack.

Verification is synchronous against a cached provider document (guard verdicts cannot await a fetch). The cached document holds the discovery fields plus the JWK set; the source single-flights concurrent fetches, never clears a good document on failure (invalidate expires freshness but keeps the last good keys, so a key-publication blip degrades to cached-key verification instead of locking the gate out), and re-reads on a `refreshMinutes` window (default 60). Verification accepts RS256 and ES256 (raw 64-byte IEEE P1363 signatures; `node:crypto` answers false, never throws, for malformed scalars). The signing algorithm comes from the **JWK**: the IAM publishes `alg` only on the EC key, so header-`alg`-driven key selection is impossible; the token header's `alg` only gates the allowed set, key type and algorithm must agree, and a JWK whose `alg` is not accepted is skipped — which also makes an HS256 downgrade structurally impossible, since no published key can carry it. `typ` is checked only when present because the real IAM omits it. `iss` must equal the discovery document's issuer and `aud` must contain `clientId` (string or array); `allowIssuerMismatch` is the documented hatch for deployments reached on a host alias of the provider URL, where signature and `aud` remain enforced and the expected issuer is taken from the token's own claim.

## Consequences

The IAM's `usk` SSO cookie is out of scope by design: `dsh` `/logout` clears only our session cookie, and a browser with a live IAM session re-lands instantly through the silent redirect — the package has no provider end-session story (the real document publishes `end_session_endpoint ` only under a key with a trailing space). The `refresh_token` in the same redirect is ignored; sessions end at `exp` (24h for this IAM) and a re-navigation restarts the silent round-trip. The fragment relay page is one inline script that runs only on the exact callback path; a headless client that POSTs the callback without completing sign-in hits the same 401 arms as a browser. `redirectPath` must match the IAM-side registration of the client (`EnterpriseDingtalk` is registered for `login.dingtalk.com`'s callback; dsh deployments register their own). Discovery fetches run server-side with `fetchTimeoutMs` and tolerate the two published document layouts (`/.well-known/openid-configuration`, then the top-level `openid-configuration.json`). The plugin is opt-in like `auth-jwt`: no shipped bundle enables it, and enabling it is one cordis.yml row (`issuer`, `clientId`, plus `secureCookie: true` behind TLS). Tests stand up a fake IdP over real sockets (discovery + JWKS endpoints, a hot key set that proves rotation lands within one window, JWKS-only outage) and drive the full Loader composition: authorize parameters, state cookie posture, forwarded-proto origin, cookie/Bearer/upgrade channels, fixation and forged-state refusal, oversized-body 413, error passthrough, secureCookie posture, and disposal. `auth-core` reaches per-file 100% coverage; `auth-iam` too, through unit suites (`id-token.ts`, `discovery.ts`), a partial-config hand-built suite that pins the direct-`apply` defaults, and the composed-host suite.

## Alternatives considered

Authorization-code flow was rejected because this IAM registration speaks implicit (`response_type=token`) and no client secret is issued to the Dingtalk-facing client; adding the confidential flow would require credentials that do not exist for this deployment. Letting the browser POST the fragment to an arbitrary path was rejected in favor of an exact-path same-origin page: the relay only exists at `redirectPath`, and the state cookie plus `SameSite=Lax` keep it unspoofable. Storing claims in a dsh-minted session cookie was rejected because the id_token is already exp-bounded, aud-restricted, and signed: re-signing it would add a second trust root with no added revocation power. Checking the token header's `alg` against a configured allowlist and trying every key was rejected: with the real set (RSA key without `alg`) that would let an EC key answer an RS256 header; JWK-driven algorithm selection plus kty agreement is the only assignment that both verifies the IAM's tokens and keeps the algorithms disjoint. Reading `state=null` back as "no state configured" was rejected — the provider echoes the literal string `null` when none was sent, and any echo that does not match our cookie's state refuses sign-in.
