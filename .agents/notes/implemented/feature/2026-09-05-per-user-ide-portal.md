# Agent Note: Per-user IDE provisioning portal

Status: implemented

English | [中文](2026-09-05-per-user-ide-portal.zh.md)

## Problem

Enterprise users reaching a personal DSH IDE meant an operator hand-running `docker run` on 10.1.17.58 per person. The requirement ([0007](../../../../docs/containerization/0007-per-user-ide-requirements.md)) is: after the company IAM signs a user in, derive `ide-<employee-number>.jereh-pe.cn` from the verified token, reconcile the container behind the never-edited nginx-proxy (C3), provision or start it through the only host executor Jenkins (C9), stream every step live into the page, and hand the browser over on health. Open questions the shipped code settles: what executes host mutations, how progress crosses into the browser, and how the portal survives its own restart.

## Decision

`@deepseek-ai/dsh-ide-portal` (apps/ide-portal) is a standalone Node application, not a webserver-plugin fiber: the portal owns the listener and has no Cordis runtime to mount a gate into. It reuses the shipped gate's pure parts — `verifyIdToken` plus the discovery-backed provider source from `dsh-host-auth-iam` (through the declared `./src/*` exports), and the cookie/body/redirect helpers from `dsh-host-auth-core` — and composes them into its own routes; the IAM specifics its module hardcodes are protocol facts for this one provider (implicit flow, fragment relay page, origin-composed unregistered `redirect_uri`, C10).

Jenkins is the only host executor. The progress channel is the build console: `Jenkinsfile.ide-provision` ships `docker/ide-provision/provision.sh` to the host and pipes the model key through the ssh session's stdin on create, and the script prints `[DSH_STEP] <seq> <step> <ok|fail|info> <detail>` markers — one line per host step, interleaved plain console text tolerated. The portal tails Jenkins' progressive console (`?start=<offset>`), parses markers into the append-only step log, and fans them out over SSE with a full replay on (re)connect; the state machine (0007) advances on marker semantics, not wall time. This keeps Jenkins the source of truth (no second protocol between portal and host), keeps `probe` builds seconds long, and makes N2's 2-second step latency a tail-cadence knob.

Per-uid correctness is three layers: the portal's in-process busy set (joiners await the owner's terminal state, never trigger), Jenkins `disableConcurrentBuilds` (host mutations serialize globally), and `docker run --name ide-<uid>` collision tolerance in the script (two racing builds converge to "already created → start/probe"). A marker file per uid (`--state` dir, named volume) records the last triggered build; on boot the portal re-attaches and tails unfinished builds, so a portal restart mid-provision loses neither the run nor the log (N3).

The uid is `sub` cross-checked against `userId` under the configured pattern at two layers — the portal refuses to derive a domain otherwise (SR1), and the host script re-validates before any interpolation (defense behind the Jenkins-parameter allow-lists). The platform key (FR10) lives only in the Jenkins Secret text credential `ide-model-key`; the create-stage build binds it with `withCredentials`, stages it under `umask 077` in the workspace, and pipes it through ssh stdin → host 0600 env file → `docker run --env-file` → immediate unlink; the portal holds and sends no key, no create succeeds without the binding, and no layer inverts into a console line, argv, or a persisted build parameter (SR5).

## Consequences

The portal is deployed by hand once (`docker/deploy-ide-portal.sh`, config `docker/ide-portal/portal.example.yaml`) behind the same proxy with `VIRTUAL_HOST=ide.jereh-pe.cn`; it is not self-provisioned. It binds `bindHost: 0.0.0.0` because the proxy reaches containers over `dc_default` (0005) — the loopback rule is dsh web's, not every service's. The console-text channel means a Jenkins outage freezes the live view but not the truth: the next reconcile re-reads Docker state. The marker-file resume is best-effort: a build that finished while the portal was down surfaces on the next enter as an ordinary reconcile. The start page is a static SPA with zero framework build (`web/`), which satisfies the front/back split without a bundler. The entry auto-checks on arrival: the reconcile probe is read-only (it reads Docker state and changes nothing), so it runs without a click (requester decision, 2026-09-06: read-only operations are automatic; this supersedes and removes the earlier dual-mode `autoCheck` switch). The probe answer renders on the page — a healthy container shows the ready status line and the open button, an absent one the check button — and neither the page nor the entry ever provisions or navigates on its own: provisioning is the click on the check button, the jump to the IDE the click on the open button. Where the server cannot reach the IAM, `iam.trustFile` names a JSON file carrying the provider's two published documents (`discovery`, `jwks`) captured from any network that can: the portal then never fetches, and sign-in plus verification run on the seeded issuer, endpoints, and keys (an operator re-captures the file after an IAM key rotation, or tokens signed with new keys are refused). The shipped gate accepts the same file as `trustFile` (read from `IAM_TRUST_FILE`, defaulted to the mounted `/etc/ide-portal/iam-trust.json`), and `provision.sh` mounts the host's seeded file read-only into every user container — a container network without egress to the IAM signs in and verifies fully offline. Tests stand in the IAM (real RSA JWKS over a local HTTP server), offline verification with a fetch that must never be called, and Jenkins (scripted marker builds); `tests/e2e.spec.ts` drives the real CLI process over loopback against real-socket fakes of both — sign-in round-trip, the check-button run to READY with its SSE replay, the stopped and healthy short-circuits, the always-on read-only entry check, the marker-file attach, and the offline trust-file boot with its fail-loud issuer refusal — with no test seam inside the portal and no credential stored; `docker/ide-provision/provision.sh` is exercised hermetically with `docker`/`curl` fakes; the cold path against the real host is rollout step 2 in 0008. User containers carry the shipped IAM gate (O2): `docker/dsh-aio/dshhome/iam-gate.cordis.patch.yml` mounts `auth-iam` through the entrypoint's `--patch` layer when `DSH_IAM_GATE=1`, which the provisioning script always sets, and the health probes accept the gate's `302`/`401` answer; containers launched without the switch stay open, so nothing existing changes. Idle reclamation (O4), TLS (O5), and resource caps (O7) stay parked per the requester's direction.

## Alternatives considered

Mounting `dsh-host-auth-iam` as a Cordis plugin was rejected: it would drag the whole webserver fiber (and a second listener the portal does not own) into a service whose whole job is routes plus SSE. Portal-side SSH to the host was rejected because Jenkins already owns host access, credential injection, audit trail, and serialized builds (the 0008 constraint C9 records the requester's choice). A dedicated machine-readable protocol between portal and job was rejected in favor of console markers: the console is already progressive, already retained, and adding a parallel channel creates a second source of truth for what happened. Redis or a database for the step log and locks was rejected — the run log is Jenkins' console, the host truth is Docker, and the only portal-local state is one small marker file per uid.
